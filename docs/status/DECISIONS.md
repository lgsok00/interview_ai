## 공개 대상별 계정 UI와 AI 요청 제한 정책안 (2026-10-02)

상태: 일반 공개에 대한 설명 이후 사용자가 회원가입 선행 개발을 요청해 **일반 공개 기준으로 회원가입 UI 구현·검증을 완료**했다.
내 계정 UI도 같은 날 구현·검증을 완료했다. 아래 AI 제한값은 초기 운영 권장값이며 사용자 확정값이나 구현·검증 결과가 아니다. 제한 시범 운영의 참여 확인은 현재 개발 대상에 적용하지 않는다.

### 실제 구현과 차이

- `frontend/src/App.tsx`에 공개 회원가입 경로 `/signup`과 보호된 내 계정 경로 `/account`를 추가했다. 홈에서 계정 화면으로 진입한다.
- 가입, 내 정보 조회·닉네임 변경, LOCAL 비밀번호 변경, 탈퇴 API는 구현돼 있다. 이메일 변경·비밀번호 찾기·계정 연결 API는 없다.
- `AuthService.signup`은 공개 가입을 허용하며 Google·GitHub 로그인은 처음 방문한 사용자를 자동 생성한다. 초대·참여 대상 검사는 없다.
- 초기 질문과 초안은 비동기 작업, 답변 평가는 별도 요청으로 등록하는 비동기 작업이다. 답변 저장은 평가를 자동 등록하지 않는다.
- 꼬리 질문은 동기 외부 호출이다. 기존 결과는 재사용하지만 동시에 들어온 요청은 저장 이전에 각각 외부 호출할 수 있다.
- 사용자별 일일 횟수·공통 대기 작업 제한은 없다. `InterviewGenerationDeadline`의 JVM 내 Semaphore 4개는 사용자별 제한도 여러 서버의 공통 제한도 아니다.
- 확인한 작업 시작 HEAD는 `18154fd` (`main`)이며 작업 트리는 깨끗했다. 이력서 보완 구현·테스트·문서는 이미 커밋됐다.

### 공개 대상별 화면 범위

다음 표는 정책 검토 당시의 대상별 비교다. 현재 진행 기준은 일반 공개이며 회원가입·내 계정 UI는 완료했다. 제한 시범 운영의 권장 표시는 최초 비교 당시 기준이다.

| 공개 대상                   | 가입·접근 정책                                                                       | 첫 배포의 계정 UI                                             | 후속 범위                                                                    |
|-------------------------|--------------------------------------------------------------------------------|---------------------------------------------------------|--------------------------------------------------------------------------|
| 본인·포트폴리오 시연             | 시연자 계정만 허용. 공유 계정에 실제 개인 문서를 넣지 않는다                                            | 내 정보 조회·로그아웃. 계정 변경·정리는 운영자가 수행                         | 외부 사용자 참여 시 제한 시범 운영 범위로 전환                                              |
| 소수 지인·테스터 제한 시범 운영 — 권장 | Google·GitHub 중심, 서버의 허용 이메일 목록으로 가입·로그인·재발급·인증 요청을 제한. LOCAL 신규 가입은 서버에서 비활성화 | `/account` 내 정보·닉네임 수정·탈퇴. 기존 LOCAL 참여 계정에는 비밀번호 변경도 제공 | 일반 공개 회원가입·비밀번호 찾기                                                       |
| 누구나 가입하는 일반 공개          | LOCAL 가입 화면과 소셜 첫 로그인 가입 모두 제공                                                 | `/signup` 및 `/account` 내 정보·닉네임 수정·LOCAL 비밀번호 변경·탈퇴     | 이메일 변경·계정 연결·이메일 인증·비밀번호 찾기는 별도 계약과 구현 필요. 복구 미지원 사실과 운영 문의 경로를 공개 전에 안내 |

제한 시범 운영은 링크 비공개나 가입 버튼 숨김으로 구현하지 않는다. 허용 이메일은 trim·소문자 정규화하고 Google·GitHub의 검증된 이메일을 사용한다.
신규 생성·토큰 발급 전에 허용 여부를 검사하고, 기존 계정의 로그인·Refresh Token 회전·JWT 인증 후 DB 사용자 검사에도 적용한다. 허용 목록 제거 후 기존 Access Token도 차단한다.
계정 삭제 시 사용량이 초기화되지 않도록 AI 한도의 주체는 시범 운영 참여 식별자에 연결하고 사용자 ID는 현재 계정의 소유권 확인에 사용한다.
참여 식별자는 정규화 이메일의 서버 HMAC처럼 원문 이메일을 사용량 테이블에 복제하지 않는 방식으로 유지하며 운영 중 키를 임의 변경하지 않는다.
탈퇴 후 같은 이메일의 재가입은 기존 정책대로 허용하되 같은 날 사용량은 이어받는다. 일반 공개도 동일 정책을 적용하며 여러 이메일을 이용한 우회는 전역 제한으로 보완한다.

계정 UI는 기존 DTO 검증을 따른다. 닉네임은 trim 후 2~50자, LOCAL 새 비밀번호는 8~64자이며 현재 비밀번호와 동일하면 거부한다.
이메일·provider는 읽기 전용이며 OAuth 사용자에게 비밀번호 변경 입력을 제공하지 않는다. LOCAL 가입 이메일은 기존 서버 정규화를 유지한다.
비밀번호 변경 성공 시 모든 Refresh Token이 폐기되므로 현재 기기의 cookie를 로그아웃 API로 정리하고 메모리 토큰·인증 상태를 비운 뒤 재로그인을 안내한다.
다른 기기의 기존 Access Token은 만료 전까지 유효한 현재 서버 계약을 유지한다. 탈퇴는 개인 문서·면접 기록 삭제와 소셜 제공자의 앱 연결 미해제를 확인 문구로 안내한다.
마지막 활성 관리자 탈퇴 등 서버 오류는 그대로 표시하며 실패 시 인증 상태와 편집 내용을 유지한다.

### AI 접수 한도 — 초기 권장값

사용자별 하루 한도는 모든 provider·역할에 동일하게 적용하며 ADMIN도 사용자 생성 경로에서 면제하지 않는다.
기간은 **Asia/Seoul 00:00~다음 날 00:00**이다. DB UTC 시각 한 번으로 사용일·다음 초기화 시각을 계산하고 저장 시각은 UTC로 유지한다.
운영 수치와 공개 모드는 서버 설정으로 관리하며 UI에 하드코딩하지 않는다. 아래 값은 토큰·요금 측정으로 도출한 예산 보장값이 아니라 초기 접수량 기준이다.

| 기능          | 시연 / 제한 시범 / 일반 공개 일일 한도 | 차감 대상                                                                                          |
|-------------|--------------------------|------------------------------------------------------------------------------------------------|
| 초기 면접 질문    | 1 / 3 / 3회               | `POST /api/interview-sessions`, `POST /api/interview-sessions/{sessionId}/generation/retry` 접수 |
| 꼬리 질문       | 5 / 15 / 15회             | `POST /api/interview-sessions/{sessionId}/questions/{questionId}/follow-up`의 새 생성 시도           |
| 답변 평가       | 10 / 30 / 30회            | `POST /api/interview-sessions/{sessionId}/answers/{answerId}/evaluation` 및 `/retry`의 새 작업 접수   |
| AI 자기소개서 초안 | 1 / 3 / 3회               | `POST /api/cover-letters/{coverLetterId}/drafts` 및 `/{draftId}/regenerate`의 새 작업 접수            |

- 제한 시범·일반 공개는 초기 질문 5개와 꼬리 질문 최대 5개인 면접 3회의 최초 평가를 허용하는 기준이다. 실패·수동 재시도는 같은 한도를 소비하므로 항상 3회 완주를 보장하지 않는다.
- 네 기능 합산 **사용자별 대기·실행 2건**, **전체 대기·실행 50건**, **전체 일일 접수 500건**을 초기 권장값으로 둔다. 전역 일일 한도도 같은 KST 날짜를 사용한다.
  사용자별 한도가 남아 있어도 전체 한도를 넘으면 신규 접수를 차단한다. 새 날이 돼도 기존 대기·실행 슬롯은 초기화하지 않는다.
- 초기 질문 `PENDING/RUNNING`, 평가 `PENDING/PROCESSING`, 초안 `PENDING/RUNNING`과 예약된 동기 꼬리 질문을 슬롯에 포함한다. 자동 재시도 대기도 같은 슬롯을
  유지한다.
  `READY/REVIEW_READY/COMPLETED/FAILED` 등 종료 결과와 초안 검토·적용 대기는 슬롯에서 제외한다. 면접 `IN_PROGRESS` 자체는 AI 실행 슬롯이 아니다.
- 사용자 요청은 **새 작업을 실제 접수할 때 1회** 차감한다. 타인 접근·입력/상태 오류·설정 비활성·한도 거절·DB 롤백은 차감하지 않는다.
  접수 후 모델 실패·timeout·fallback 결과는 차감 유지한다. 자동 worker 재시도·lease 재선점은 추가 접수 횟수를 차감하지 않으며 기존 최대 시도 정책을 유지한다.
- 기존 평가·꼬리 질문 결과 반환은 차감하지 않는다. 생성 POST는 현재 멱등성이 없으므로 각각의 새 접수는 차감한다. UI 자동 재전송은 금지하고 통신 결과가 불명확하면 목록·상태를 먼저 확인한다.
- 동기 꼬리 질문은 `(sessionId, questionId)`별 실행 예약을 두어 외부 호출 전에 중복을 막는다. 같은 실행 중 요청에는 409 `AI_REQUEST_IN_PROGRESS`를 반환하고 차감하지
  않는다.
  실패 후 명시 재요청은 다시 차감한다. 실행 예약은 성공·실패·timeout에 종료하며 프로세스 종료는 lease 복구로 정리한다. 외부 요청의 실제 취소·exactly-once는 보장하지 않는다.
- 최초 질문·평가의 기존 수동 재시도 최대 2회, 초기 질문당 꼬리 질문 하나, 추가 깊이 금지는 유지한다. 한도를 이유로 재시도 횟수를 초기화하지 않는다.
- 답변 저장·세션 시작/완료·기존 결과와 성장 분석 조회·초안 검토 수정/명시 적용에는 Chat 접수 횟수를 차감하지 않는다. 한도 소진 후에도 답변과 검토 내용을 저장할 수 있다.
  초안 적용이 등록하는 RAG embedding은 아래 별도 비용 통제를 따른다.

### 구현 위치와 장애 계약

- 새 `ai/usage` 공통 서비스·Repository·설정과 **새 Flyway migration**으로 일일 참여자/전역 사용량과 실행 예약을 영속화한다. 현재 마지막 migration은 V20이며 구현 시
  다음 번호를 다시 확인한다.
  Redis는 MVP 필수 의존성으로 추가하지 않는다. Controller/filter에서만 한도를 확인하는 방식은 내부 서비스 호출과 동시 요청을 보호하지 못한다.
- 사용자·공개 범위 확인 → 사용량의 전역 행 → 참여자 행 → 기존 도메인 행 순서로 잠금 규칙을 맞춘다. 당일 행 최초 생성은 unique와 원자적 insert/upsert로 경합을 처리한다.
  소유권·입력·설정·상태·기존 결과 판정 뒤 같은 트랜잭션에서 한도 확인·차감·실행 예약·작업 등록을 확정한다. 거절은 도메인 상태를 바꾸지 않는다.
  기존 탈퇴·관리자·문서 잠금 순서와의 경합은 구현 단계에서 대조하며, 읽기 사전 검사만으로 소유권/상태 확정을 대신하지 않는다.
- `InterviewSessionService.create`, `InterviewGenerationExecutionService.retry`,
  `AnswerEvaluationService.request/retry`,
  `CoverLetterDraftService.create/regenerate`의 실제 작업 접수 트랜잭션에 연결한다. 특히 질문 재시도는 현재 `REQUIRES_NEW`이므로 같은 독립 트랜잭션 안에 차감이
  있어야 한다.
- `InterviewFollowUpService.generate`는 준비·실행 예약을 짧은 트랜잭션에서 확정하고 외부 호출은 트랜잭션 밖에서 수행한 뒤 기존 소유권·상태 재검사와 결과 저장을 유지한다.
  `InterviewAnswerService`의 준비/저장 단계도 예약 키와 잠금 순서를 맞춘다.
- worker의 완료·최종 실패는 작업 상태와 예약 종료를 같은 트랜잭션에서 처리한다. attempt·lease 검증으로 늦은 완료가 새 실행의 슬롯을 해제하지 못하게 한다.
  주기적 복구는 실제 작업 상태와 lease를 대조하며 단순 TTL 만료로 살아 있는 비동기 작업의 슬롯을 해제하지 않는다. 계정 삭제와 슬롯 정리도 같은 잠금 순서를 따른다.
- 사용자 일일 초과는 429 `AI_DAILY_LIMIT_EXCEEDED`, 사용자 슬롯 초과는 429 `AI_PENDING_LIMIT_EXCEEDED`다.
  전체 접수/슬롯 포화는 503 `AI_CAPACITY_EXCEEDED`, 사용량 저장소 장애는 503 `AI_USAGE_UNAVAILABLE`로 신규 유료 요청을 차단한다.
  기존 `GlobalExceptionHandler`·`ErrorResponse(code, message, errors)` 형식을 유지하며 message에 한도·회복 조건을 안내한다.
  일일 초과 응답에는 다음 KST 자정까지의 `Retry-After` 초를 제공한다. 슬롯 해제 시각은 확정할 수 없으므로 메시지로 진행 작업 완료 후 재시도를 안내한다.
- 새 `GET /api/ai/usage`는 본인의 기능별 limit/used/remaining, active/activeLimit, resetAt을 제공한다. 전역 참여자 사용량과 개인 원문은 노출하지 않는다.
  화면은 표시용이며 서버가 최종 판단한다. 429/503은 자동 재전송·인증 재발급 대상으로 삼지 않고 입력을 보존한다. 사용량 조회 실패는 생성 일시 중단과 새로고침을 안내한다.
- backend 공개 실행에서는 한도 적용을 필수로 하고 잘못된 제한값·미설정 참여 목록은 시작 단계에서 거부한다. 개발·테스트 비활성화는 명시 설정으로만 허용한다.

### 배포 계층과 embedding 비용

- 배포 계층은 인증 경로 IP당 분당 10회, 신규 AI POST 사용자당 분당 10회·IP당 분당 30회를 초기 권장값으로 둔다. 여러 창·NAT를 고려해 일일 한도는 IP가 아닌 참여자로 판단한다.
  프록시의 사용자 키는 검증된 인증 정보로만 만들고 임의 사용자 헤더는 신뢰하지 않는다. 사용자 키를 검증할 수 없는 프록시는 IP 제한만 수행하고 사용자 속도 제한은 서버에서 구현한다.
  refresh·logout과 OAuth redirect 왕복은 로그인 실패 시도 제한과 구분하며 최종 라우팅·저장소·다중 서버 동작은 배포 설정 단계에서 확정한다.
- Chat 일일 접수량은 RAG embedding·토큰별 비용을 제한하지 않는다. 개인 문서의 새 RAG UPSERT를 만드는 생성/수정/버전 복원/초안 적용은 참여자별 하루 20회로 별도 제한하고,
  대표 설정·원본 조회·삭제·회원 탈퇴의 DELETE 정리는 제한하지 않는다. 변경 트랜잭션과 같은 사용량 차감/롤백을 사용한다.
  관리자 카탈로그 변경·재색인은 관리자별 분당 10회로 제한하고 RAG backlog·오류·실제 호출량을 관측한다. 청소 DELETE는 비용 제한 때문에 중단하지 않는다.
- 전역 설정으로 신규 Chat 접수와 신규 embedding을 각각 중단할 수 있게 한다. embedding 중단 중 새 UPSERT를 만드는 문서 변경은 명시적으로 거절하고 DELETE 정리는 유지한다.
  이미 접수한 Chat 작업의 실행 중단/재개는 worker 활성 설정과 함께 운영한다. RAG UPSERT 중단 시 DELETE가 뒤에서 막히지 않도록 선점 정책도 분리한다.
  공급자 사용량·월 예산 알림·입출력 토큰 상한·전체 worker 실행 동시성은 배포 운영 설정에서 정한다. 500건 제한을 금액 상한이라고 표현하지 않는다.

### 적용 순서와 검증 기준

1. 일반 공개 기준 회원가입·내 계정 UI는 완료했다. 이메일 인증·비밀번호 찾기의 공개 전 도입 범위 또는 복구 미지원 안내·문의 경로를 결정한다. 허용 이메일 목록은 적용하지 않는다.
2. 새 migration·설정·원자적 사용량/슬롯 예약 기반을 구현하고 네 생성 서비스와 worker 종료·복구를 연결한다. 사용량 API·UI 안내와 RAG 비용 통제를 적용한다.
3. 사용자가 애플리케이션 코드를 반영하면 Codex가 실제 변경을 확인하고 테스트를 작성한다. 사용자가 Gradle Wrapper와 frontend 명령을 실행한 결과로 검증한다.
4. 구현·검증 후 배포 플랫폼·HTTPS·cookie/CORS/OAuth callback·전역 worker 동시성·proxy 속도 제한과 실제 비용 관측을 구성한다.

예정 검증은 정상 가입/내 정보/닉네임/LOCAL 비밀번호/탈퇴, provider별 화면·검증 경계, 인증 만료·중복 이메일·잘못된 현재 비밀번호·마지막 관리자 보호를 포함한다.
제한 운영은 미허용 LOCAL·OAuth 가입/로그인/refresh/기존 JWT 차단, 허용 목록 제거, 탈퇴·재가입 당일 한도 보존을 확인한다.
AI는 한도 직전/도달/초과, KST 자정, 전날 작업의 슬롯 유지, 네 기능 합산 슬롯, 동시 마지막 한도·첫 행 생성, 전역 포화, 거절 시 상태 불변과 등록 실패 롤백을 확인한다.
기존 결과 재사용·중복 꼬리 질문·자동/수동 재시도 차감·최대 횟수·timeout·worker 종료/lease 복구/늦은 완료·탈퇴 경합·저장소 오류를 검증한다.
한도 초과 뒤 답변 저장·결과 조회·초안 검토 유지, RAG UPSERT 한도·DELETE 정리 유지와 429/503 UI 복구는 HTTP/component 및 배포 전 통합 검증에 포함한다.
회원가입 UI의 HTTP 처리 테스트 20개를 작성했고 사용자 전체 Vitest 135개·lint·build 성공과 브라우저 확인 완료를 전달받았다.
내 계정 UI는 API·HTTP client 신규 테스트 26개와 사용자 전체 Vitest 161개·lint·build 성공, 브라우저 점검 완료를 확인했다.
현재 비밀번호 불일치 401은 refresh·재전송·토큰 삭제 없이 반환한다. component 상호작용·AuthProvider 상태 전환은 자동 검증하지 않으며 개별 브라우저 결과는 별도 전달되지 않았다.
AI 제한 정책에 대한 신규 구현·테스트는 없다. 기존 백엔드 1,050개와 이번 Vitest 161개 성공을 AI 제한의 검증으로 사용하지 않는다.

  로드맵을 제공한다. MVP 성장 분석은 추가 AI 호출이나 분석 결과 영속화를 사용하지 않는다.

- API base path는 현재 구현인 `/api`를 유지하며 URL 기반 버전 (`/api/v1`)은 도입하지 않는다. 외부 공개나 독립 배포 클라이언트 도입 전에 버전 정책을 다시 검토한다.
- Access Token 재발급 URI는 현재 구현인 `/api/auth/refresh`를 유지하고 Notion 명세의 `/auth/reissue`를 사용하지 않는다.
- 성공 응답은 공통 envelope 없이 endpoint별 DTO를 직접 반환하고, 목록·페이징 응답은 도메인별 전용 DTO로 정의한다. HTTP 204 응답은 body 없이 유지하며 오류 응답은 기존
  `GlobalExceptionHandler`와 `ErrorResponse` 형식을 유지한다.
- Notion 회원가입 명세의 `name`은 실제 구현의 `nickname`과 다르다.
- Notion ERD의 User에는 실제 스키마의 `provider_id`와 `refresh_tokens`가 빠져 있고 비밀번호 컬럼명도 실제 `password_hash`와 다르다.
- 기업·채용공고 API와 DB 관리자 권한 검사는 구현·검증을 완료했다. Spring AI·Qdrant·OpenAI embedding의 외부 색인과 검색 코드는 구현·선택 검증됐고 실제 네트워크 연동,
  면접·평가·성장 모듈은 아직 완료되지 않았다.
- 자기소개서 PDF 업로드와 텍스트 추출은 확정된 이력서 파일 정책을 공통화하는 후속 범위로 유지한다.
- RAG 설계의 `companyId AND jobPostingId AND userId` 조건은 기업 공용 문서와 사용자 전용 문서의 metadata가 다르므로 문서 유형별 필터 조합으로 구체화해야 한다.
